# Отчёт по проверке логики приложения

Дата проверки: 23.11.2026

## 1. Проверенные компоненты

- app/services/sales_order_service.py
- app/services/production_order_service.py
- app/models.py
- app/views/sales_order_view.py
- app/views/production_order_view.py

## 2. Заказы покупателей

### LOG-01. Отсутствует полная проверка позиций заказа
Файл: app/views/sales_order_view.py
Методы: post(), put()

Некорректные или отсутствующие product_id, а также UUID несуществующих товаров могут пропускаться без сообщения об ошибке. В результате заказ может сохраниться без части переданных позиций.

Приоритет: высокий.

### LOG-02. Не ограничена максимальная скидка
Файл: app/views/sales_order_view.py
Методы: post(), put()

API принимает скидку без проверки верхней границы. В модели SalesOrderItem ограничение CheckConstraint проверяет только discount >= 0. Скидка больше 100% может привести к отрицательной стоимости позиции.

Приоритет: высокий.

### LOG-03. Возможна ошибка при обновлении заказа без items
Файл: app/views/sales_order_view.py
Метод: put()

Переменная items_list создаётся только при наличии поля items. Далее она используется при пересчёте связанного производственного заказа. Если поле items отсутствует, но связанный производственный заказ существует и автоматическое создание производства включено, возможно возникновение UnboundLocalError.

Приоритет: высокий.

### LOG-04. Возможна коллизия номеров заказов
Файл: app/views/sales_order_view.py
Метод: post()

Номер заказа формируется через поиск максимального номера и увеличение его на единицу. При одновременном создании заказов несколькими пользователями возможна генерация одинаковых номеров. Уникальное ограничение базы данных предотвратит сохранение дубликата, но один из запросов завершится ошибкой.

Приоритет: средний.

### LOG-05. Создание заказа покупателя и производственного заказа выполняется раздельными транзакциями
Файл: app/views/sales_order_view.py
Метод: post()

Сначала выполняется commit заказа покупателя, а затем отдельный commit производственного заказа. При ошибке второго этапа заказ покупателя может остаться сохранённым без связанного производственного заказа.

Приоритет: высокий.

### LOG-06. Возможна потеря информации о выполненных работах
Файл: app/views/sales_order_view.py
Метод: put()

При пересоздании позиций связанного производственного заказа старые позиции удаляются, а новые создаются с completed_quantity=0. Это может привести к потере ранее зафиксированного объёма выполненных работ.

Приоритет: высокий.

## 3. Себестоимость и расчёты

### LOG-07. При отсутствии цены используется нулевая стоимость
Файлы:
- app/services/sales_order_service.py
- app/services/production_order_service.py

Если цена материала или операции не найдена, сервис подставляет 0.0. В результате себестоимость может быть занижена, а прибыль завышена. Пользователь не получает предупреждения об отсутствующей цене.

Приоритет: высокий.

### LOG-08. Не учитывается дата заказа при выборе цены
Файлы:
- app/services/sales_order_service.py
- app/services/production_order_service.py

При выборе цены используется последняя запись по effective_date без ограничения датой заказа. Поэтому исторические заказы могут рассчитываться по цене, которая появилась позднее даты заказа.

Приоритет: высокий.

### LOG-09. Возможна ошибка при отсутствии связанного товара
Файл: app/services/sales_order_service.py
Метод: calculate_cost()

В отличие от сервиса производственных заказов, здесь нет отдельной проверки наличия товара перед обращением к product.spec_materials. При отсутствии связанного товара возможно исключение.

Приоритет: средний.

## 4. Производственные заказы

### LOG-10. Не проверяется превышение выполненного количества
Файлы:
- app/views/production_order_view.py
- app/models.py

В модели есть ограничение completed_quantity >= 0, но отсутствует ограничение completed_quantity <= quantity. API также не выполняет такую проверку при создании позиции.

Приоритет: высокий.

### LOG-11. Некорректные позиции могут пропускаться
Файл: app/views/production_order_view.py
Метод: post()

Если UUID товара имеет неверный формат, позиция пропускается через continue. Заказ при этом может быть сохранён без переданной позиции.

Приоритет: средний.

### LOG-12. Отсутствует обновление состава производственного заказа
Файл: app/views/production_order_view.py
Метод: put()

Метод обновляет номер, дату, подразделение и статус, но не обрабатывает поле items. Если по требованиям проекта состав производственного заказа должен редактироваться через этот API, функциональность отсутствует.

Приоритет: средний. Требует сверки с требованиями проекта.

### LOG-13. Недостаточная обработка ошибок даты
Файлы:
- app/views/sales_order_view.py
- app/views/production_order_view.py

Используется date.fromisoformat(). Некорректная дата может вызвать исключение. Явная обработка ValueError в соответствующих местах не обнаружена.

Приоритет: средний.

## 5. Положительные результаты проверки

- В моделях используются внешние ключи и ограничения целостности.
- Количество позиций заказов должно быть больше нуля.
- Цена позиции не может быть отрицательной.
- Удаление используемого товара ограничено через ondelete=RESTRICT.
- Статус производственного заказа ограничен допустимыми значениями.
- Сервис производственных заказов отдельно обрабатывает отсутствие связанного товара.

## 6. Общий вывод

В ходе проверки обнаружены недостатки валидации входных данных, обработки ошибок, генерации номеров заказов и расчёта себестоимости.

Наиболее важными являются:
- возможность некорректной скидки;
- ошибка при обновлении заказа без списка позиций;
- раздельное сохранение заказа покупателя и заказа на производство;
- потеря данных о выполненном количестве;
- использование нулевой цены при отсутствии записи;
- выбор цены без учёта даты заказа.

Часть замечаний требует дополнительного тестирования и сверки с требованиями проекта. Исходный код в рамках проверки не изменялся.
